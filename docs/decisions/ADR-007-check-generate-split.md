## Context

Derived exemplars are generated by a real model and validated by an LLM judge — but CI must be hermetic, and prod must never rewrite the character's corpus unsupervised. A naive design either puts model calls in CI (flaky, slow, expensive) or lets a scheduled job regenerate corpus in prod (unauditable character change).

## Decision

Split checking from generating:

- **`thea2 corpus:check` — CI, hermetic, no model.** Verifies the committed corpus against `corpus/derived/manifest.json`: zero dirty targets (every expected deriveKey has a manifest entry), zero orphans, every derived file's content hash equals its id, every entry has `judge.pass = true`, and fan-out caps hold (mood variants ≤ 6 per scene; derived:canon ≤ 8:1).
- **`thea2 derive` — dev, manual, real model + judge.** Enumerates the dirty set from canon hashes × generator fan-out rules, regenerates, judges, GCs orphans (emitting `derive.orphan_gc`; git history is the recovery path), and rewrites the manifest. Output is committed and reviewed like any code change.
- **Prod.** The weekly derive-check job only *reports* dirtiness as an alarm event. Prod never auto-mutates the corpus.

## Consequences

- CI stays deterministic and model-free while still guaranteeing that the corpus on main is exactly what the manifest attests: judge-approved, byte for byte.
- Every corpus change is a reviewable git diff; character drift via derivation has an audit trail.
- A canon edit leaves CI red (dirty targets) until someone runs `thea2 derive` and commits the result. That friction is the feature: no derived output lands without a human in the loop.
- Judge nondeterminism is quarantined to dev time; bumping a generatorVersion dirties that generator's whole family via the deriveKey, forcing a full, reviewed regeneration.
